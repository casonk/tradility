# Changelog

## [Unreleased]

- Add a standalone, loopback-only web application (`tradility-web`, optional `web` extra) that owns the full indicator/detail interface previously available only through Clockwork. It serves bounded analysis lists and exact-ticker details, owner-only manual order state merged with broker exports, CSRF-protected mutation routes, optional refresh commands, and a narrow proxy to the existing credential-holding trader service. Clockwork navigation, portfolio targets, and consolidated finances are optional integrations rather than requirements.
- `GET /accounts` lists `banks`: checking, savings and money-market accounts from the finance pipeline's bank statements (`exports/bank/<bank>/timeseries-*.csv`, beside the investment export), each with its newest statement's balance, date, and that period's money in, money out and interest. Only the last digits are kept; closed accounts and liabilities are left out; balances are as of the statement date. They are not part of the investment position totals.
- Each ticker record carries `indicator_variants`: RSI over 7, 14 and 21 bars, VWAP over 10, 20 and 50, and simple moving averages over 20, 50, 100, 200 and 300 (null when the history is too short), so a consumer can offer other windows. The standard `rsi_14`, `vwap_20`, `sma_50` and `sma_200` fields are unchanged.
- Fundamentals: a short interest of 0.0 (what Schwab reports for most names) is read as unknown rather than as a neutral rule, so it no longer dilutes the rating.
- Fix: the scheduled run attached no fundamentals because it passes no flags and the fundamentals fetch ignored `TRADILITY_SCHWAB_ACCESS_TOKEN` / `TRADILITY_SCHWAB_TOKEN_COMMAND`, which the price fetch already reads. It now uses the same fallback.
- Schwab fundamentals. The analysis attaches `fundamentals` (P/E, PEG, ROE, margins, growth, leverage, liquidity, coverage, yield, short interest, beta, market cap, EPS) to each company from Schwab's instruments endpoint, with `fundamental_signals` (up to ten buy/neutral/sell rules and their thresholds), `fundamental_score` and a `fundamental_rating`, separate from the technical rating. Zero from Schwab means unknown; at least four rules are needed for a rating; funds and ETFs get figures only. Needs the Schwab token already used for prices; a failing request skips fundamentals and never fails the analysis.
- Statement accounts use the newest balance the finance pipeline has: where its per-account series (`fid/timeseries-*.csv`, next to the holdings export) reaches a later period than the position rows, that ending balance replaces the account's total and as-of date (new statements are PDFs with balances but no position rows). Positions still come from the holdings export. An account is matched by its last digits and its type (two Fidelity accounts share 7866), and a recent account the position rows never mention, such as the 401(k) or crypto, is added with its balance and no positions.
- The Fidelity browser refuses to open the trade page while a consumer VPN is connected: Fidelity answers a login from a VPN address with "we can't complete this action right now" (found when this host's traffic was going through NordVPN), and every refused attempt counts against the account. Pause the VPN, or set `TRADILITY_FIDELITY_ALLOW_VPN=1` to try anyway.
- Fidelity by browser, off by default (`[fidelity] automation = "off" | "stage" | "submit"`). `tradility.fidelity_browser` drives Fidelity's trade ticket on a persistent browser profile you sign in to yourself (`python -m tradility.fidelity_browser login`; no password or one-time code is ever typed by this code). `POST /fidelity/stage` runs the policy checks and the ticket, fills Fidelity's page, presses its Preview and verifies the preview against the order (symbol, action, quantity, price, type, duration, account), stopping on any difference; `POST /fidelity/submit` presses the final button once on a verified page, only in `submit` mode, after the usual confirmation, counted toward the daily cap, with an unknown outcome recorded and never retried. The browser runs in a helper process under the system Python so the service needs no browser library. Unofficial: it may breach Fidelity's terms and depends on the page layout; tested against a local mock only. Active Trader Pro is a Windows-only desktop program and is not driven.
- Fidelity, assisted. Fidelity has no order API for individuals (and SnapTrade's connection is read-only), so nothing is ever sent there. `POST /fidelity/ticket` checks an order against the trading policy (the Fidelity accounts listed under `[fidelity] accounts`, the ticker allowlist, per-order cap, price band, live price from Schwab) and Fidelity's own rules (day or good-till-canceled, extended hours only for day limit orders, whole shares for limit orders, GTC lasts 60 days), lays it out in Fidelity's fields, and shows how it changes the position using the statement holdings (statement accounts are now listed one by one, with the as-of date). You then submit it on Fidelity's trade page. The audit log records the ticket; it never counts toward the daily cap because nothing was sent. `GET /status` lists the Fidelity accounts.
- Schwab holdings carry their average price (Schwab's own `averagePrice` for the position) and `GET /holdings/<ticker>` returns it per account as `average_price`, so what a position cost can be read live instead of from statements that may lack a cost basis.
- Fix "$0 to trade": the account feed took Schwab's `initialBalances.cashAvailableForTrading`, which is 0.0 outside the opening snapshot, as what an account can spend. An account now reports `spendable` (Schwab's projected stock buying power, which already reserves for open orders, else the current buying power) and the preview's "cash after" uses the cash balance and "buying power after" uses `spendable`. `cash_available_to_trade` is gone. A preview also lists the symbol's holdings in every account (the chosen one before and after), and `GET /holdings/<ticker>` returns where a ticker is held now, per account plus statement institutions.
- The preview's position impact now says what it counts. `overall` is every account read live (the Schwab accounts and Binance.US); a new `everything` also adds institutions that are only known from statements in the holdings export, such as Fidelity, using their statement values and showing the statement date, since those can be months old. `GET /accounts` lists those institutions under `statements`.
- Fix Schwab's own words in a preview: its validation entries carry their text in `activityMessage`, so a rejection showed only "rejected" and warnings never appeared. A preview now says, for example, "You do not have enough available cash/buying power for this order."
- An order preview shows how the order changes the position: dollars, shares and the percentage of the account and of everything you own (all Schwab accounts plus Binance.US), before and after, plus the cash and buying power left in the account. A buy adds its cost to the position and a sell removes it; paying moves cash into stock, so an account's total is unchanged and only its mix shifts. It is skipped, not an error, when account details are unavailable. New policy `[defaults] confirmation = "phrase" | "button"`: with `button` the order is sent by clicking Place order on the preview (still single-use and two-minute); cancellations and withdrawals always need their typed phrase.
- Order templates: `GET /quote/<ticker>` also returns a price for each template, one-click order shapes the policy defines under `[[templates]]` (name, side, offset from the mark, optional duration and hours). With none configured the built-in set is buy 1, 2, 4 and 8% under the mark and sell 1, 2, 4 and 8% over. Prices land on the pair's tick for Binance.US.
- Every Schwab duration and session is covered. Durations: day, good till cancelled, fill or kill, immediate or cancel, end of week, end of month and next end of month. Sessions: regular, extended (`SEAMLESS`, pre-market through after-hours), pre-market only (`AM`) and after-hours only (`PM`). Day and GTC with regular or extended hours are the familiar DAY, DAY EXT, GTC and GTC EXT. Rules checked before the broker is asked: pre-market, after-hours and extended orders must be limit orders and day or GTC; a market order is regular hours and cannot rest (day, fill or kill or immediate or cancel). A market order with no duration given defaults to a regular-hours day order. The orders export also records each broker order's duration and session.
- Schwab orders take a configurable trading session and duration: regular or extended hours (Schwab's `SEAMLESS` session, pre-market through after-hours) and good-till-cancelled or day. The policy's `[defaults] session` and `time_in_force` fill in whatever a request leaves out (the order form starts from them); each order can override them. A market order cannot be placed in extended hours. Both are shown in the preview and recorded in the audit log. Binance.US spot orders are unchanged (good till cancelled, 24/7).
- Add deposit and withdrawal history (`tradility.transfers`, `GET /transfers`, read-only: Schwab cash movements and Binance.US deposits and withdrawals over a year, addresses cut to their last six characters) and Binance.US withdrawals, off by default behind their own `[withdrawals]` policy switch: only to allowlisted destinations, per-withdrawal and daily caps (unknown outcomes count, never retried), a preview with a balance check, a typed `WITHDRAW <amount> <coin> TO <label>` confirmation and the audit log. They use a separate credential command (`TRADILITY_BINANCE_WITHDRAW_CREDENTIAL_COMMAND`). Schwab has no money-movement API, so nothing can start a Schwab transfer.
- Binance.US orders respect the exchange's filters: the default limit prices from `/quote` land on the pair's tick size, and a preview refuses a quantity that is not a multiple of the lot step, a price off the tick, or an order under the minimum notional, naming what is allowed (public `exchangeInfo`, cached per pair).
- Add read-only account details (`tradility.accounts`, served live and cached for 20 s at `GET /accounts` on the trader service): for each Schwab account its type (margin or cash, so margin eligibility), total value, cash, cash available to trade, buying power, available funds, day-trading buying power, margin balance, day-trader and closing-only flags, whether it is in a call, and its position count; for Binance.US the spot balances valued in dollars, with whether the key can trade and can withdraw. GET requests only; account numbers are cut to their last four digits.
- The orders export tags each Schwab order with its account's last digits (`account`), so cancelling an open order from Clockwork can name the account.
- Trading policy: `[schwab] accounts = [...]` lists every Schwab account that may be traded and each order names one (no default, so a wrong account cannot be picked silently; `[schwab] account` is gone). `tickers = ["*"]` allows any ticker while the dollar caps and price band still apply. New `[defaults]` (`buy_offset_pct = -2.5`, `sell_offset_pct = 2.5`) and `GET /quote/<ticker>` give the order form its default: a good-till-cancelled limit order 2.5% below the current mark for a buy and 2.5% above for a sell. Schwab limit orders now rest until cancelled (`GOOD_TILL_CANCEL`); market orders stay day orders. The mark is the quote's `mark`, then its last trade.
- Fix Schwab quotes and account lookups in the trader: a GET that declared a JSON Content-Type got HTTP 400, so only requests with a body send it now. Found by a live preview-only check.
- Add order placement, off by default: `tradility.trading` and the local `tradility.trader_service` (127.0.0.1:8768). A policy file (`~/.config/tradility/trading.toml`, owner-only, fails closed) sets the enable switch, ticker allowlist, per-order and daily dollar caps, a price band and the one Schwab account. Orders are previewed (broker validation without placing), then confirmed by typing the exact phrase against a single-use two-minute token; every step goes to an owner-only audit log, and an unknown outcome counts against the daily cap and is never retried. Limit and market orders and cancel, for Schwab and Binance.US. The order reader stays GET-only.
- Order fetch: a held coin Binance.US does not list (HTTP 400 Invalid symbol) is skipped and counted as `unlisted_symbols` instead of failing the whole Binance source; other errors still fail it. The symbol cap rose to 120.
- Add read-only live orders: `python -m tradility.orders` fetches order history and open orders from Schwab (the same token command as price history) and Binance.US (signed GETs; `TRADILITY_BINANCE_API_KEY`/`TRADILITY_BINANCE_API_SECRET` or `TRADILITY_BINANCE_CREDENTIAL_COMMAND` printing `{api_key, api_secret}` JSON) and writes one owner-only `exports/tradility-orders.json` that Clockwork reads. The module only issues GET requests, never logs or stores a credential, and reports a failing source by class name only. The scheduled run fetches orders after the analysis and never fails on them (`TRADILITY_FETCH_ORDERS=0` skips it).
### Added

- Cached, sourced qualitative company/fund profiles with canonical names,
  descriptions, sector/industry or fund metadata, location, website, exchange,
  employee count, entity type, and retrieval timestamps.
- Chart-ready historical closes, calendar-period returns, 52-week range, and a
  transparent component-based technical rating for stock detail consumers.
- Schwab Trader API daily price-history adapter with an external token-command
  boundary and explicit per-ticker Yahoo fallback.
- Five-year default history, 50/200-day simple moving averages, and a combined
  long-term trend signal.
- Locked scheduled-analysis wrapper for Clockwork-owned systemd execution.

### Changed

- Scheduled and ordinary CLI analysis now enriches eligible tickers from a
  30-day Yahoo profile cache by default; `--skip-profiles` keeps price-only runs
  available.
- `--period` now accepts long horizons such as `5y`, `10y`, and `max`; legacy
  integer day counts remain supported.

## [0.1.0] — 2026-06-15

### Added

- Initial release: RSI (14-period) and rolling VWAP (20-day) indicators via yfinance
- `--holdings` flag to load tickers from `holdings-aggregate.json` (exported by a finance pipeline)
- `--tickers` flag for explicit ticker lists
- Crypto ticker mapping: bare symbols (BTC) → Yahoo Finance format (BTC-USD) at fetch time
- RSI signals: oversold / neutral / overbought
- VWAP signals: above / at / below (±0.5% tolerance band)
- JSON output: `exports/tradility-analysis.json`
- CLI entry point: `tradility`
